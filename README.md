# AI Support Agent — AmazonHelp (Hiver SDE Intern Take-Home)

An AI support agent for **@AmazonHelp** (from the Kaggle *Customer Support
on Twitter* dataset) that, for each incoming customer message:

1. **Classifies** it into one of 7 defined intents.
2. **Drafts a reply** grounded in how AmazonHelp has historically resolved
   similar issues (retrieved from past resolved threads, not invented).
3. **Decides auto-handle vs. escalate**, with a stated, auditable reason.

Read `reports/REPORT.md` for the full write-up (problem framing, results
vs. baselines, failure analysis, and — importantly — *why the headline
numbers below are not the whole story*). Read `reports/decision_log.md`
for the non-obvious calls made along the way.

## Repo map

```
src/            core pipeline (data prep, intent classifier, retrieval/
                grounding, reply drafting, escalation policy, agent glue)
eval/           golden set builder, baselines, LLM-judge, eval harness,
                judge-vs-human agreement calibration
scripts/        sample data generator + real-Kaggle-dataset downloader
data/raw/       bundled offline sample dataset (see below) + its
                generation-time ground truth
data/processed/ cleaned (customer_message -> brand_reply) threads
data/golden/    the 196-example hand-labelled golden eval set +
                the 30-example judge/human calibration labels
outputs/        eval results, generated by running the pipeline
reports/        REPORT.md and decision_log.md
run_pipeline.py one-command end-to-end reproduction
demo.py         try a single message against the live agent
```

## Why there's a bundled sample dataset instead of the real 3M-row file

This was built in a sandboxed environment with no access to kaggle.com, so
the real dataset couldn't be downloaded automatically. `data/raw/sample_twcs.csv`
is a **220-thread, schema-identical, structurally-faithful synthetic sample**
for AmazonHelp (same `tweet_id / author_id / inbound / created_at / text /
response_tweet_id / in_response_to_tweet_id` columns, same noisy-tweet
style). It exists purely so the whole pipeline — including the golden set
and the eval harness — is **runnable end-to-end offline in under 15
minutes with zero external downloads.**

`scripts/download_real_dataset.py` documents how to swap in the real
Kaggle file. **The pipeline code (`src/`, `eval/`) is 100% agnostic to
which CSV it's reading** — same columns in, same behavior out — so running
against the real dataset is a one-flag change, not a rewrite. See
`reports/REPORT.md` → "What's misleading about my headline number" for
exactly what does and doesn't transfer from the bundled sample to the real
data.

## Setup (5 min)

```bash
git clone <this-repo>
cd hiver-support-agent
python3 -m venv venv && source venv/bin/activate   # optional but recommended
pip install -r requirements.txt

# Optional but recommended for real (non-mock) results:
cp .env.example .env
# edit .env and add your ANTHROPIC_API_KEY
export ANTHROPIC_API_KEY=sk-ant-...
```

**No API key?** The pipeline still runs — see "Running without an API
key" below — but the numbers you get are a mock-mode placeholder, not the
headline results. The report's headline numbers assume a real key.

## Reproduce headline results (<15 min)

```bash
python3 run_pipeline.py
```

This runs, in order:

1. `python3 -m src.data_prep` — builds `data/processed/threads.jsonl` from
   the raw CSV (reconstructs resolved customer↔brand threads).
2. `python3 -m eval.build_golden_set --n 200` — (re)builds the golden set.
   Already checked in at `data/golden/golden_eval.csv` (196 examples) —
   you don't need to re-run this unless you want to resample.
3. `python3 -m eval.make_calibration_drafts` — generates the fixed
   30-example draft set used for judge/human calibration.
4. `python3 -m eval.human_agreement` — scores those 30 drafts with the
   LLM judge and compares against the pre-existing human labels in
   `data/golden/human_calibration_labels.csv`.
5. `python3 -m eval.run_eval` — runs the full agent (+ both baselines) over
   the golden set, computes all metrics, and writes:
   - `outputs/eval_results.json` (machine-readable)
   - `outputs/eval_summary.md` (human-readable table)

Try a single message interactively:

```bash
python3 demo.py "@AmazonHelp my order still hasn't shown up, been 6 days"
```

## Using Gemini instead of Anthropic

Gemini has a usable free tier, so it's a good option if you don't want to
pay for Anthropic API credit. Set in `.env` or your shell:

```bash
export LLM_PROVIDER=gemini
export GEMINI_API_KEY=AIza...        # from https://aistudio.google.com/apikey
export GEMINI_MODEL=gemini-3.6-flash  # optional, this is the default
```

`pip install -r requirements.txt` already installs `google-generativeai`.
Everything else (`run_pipeline.py`, `demo.py`, the eval harness) works
identically regardless of which provider you pick — `src/llm_client.py` is
the only file that knows which API it's calling.

## Using xAI / Grok

xAI's API is OpenAI-compatible, so this repo can call Grok through the
same provider wrapper. Set:

```bash
export LLM_PROVIDER=xai
export XAI_API_KEY=xai-...
export XAI_MODEL=grok-4.6
```

As of September 2026, xAI API usage is billed per token; the console
playground is available for testing. If your account has credits, the same
pipeline commands work unchanged.

## Using Groq

Groq is also OpenAI-compatible and can be used with the same pipeline:

```bash
export LLM_PROVIDER=groq
export GROQ_API_KEY=gsk_...
export GROQ_MODEL=openai/gpt-oss-20b
```

The Groq base URL is `https://api.groq.com/openai/v1`. You can swap
`GROQ_MODEL` for another active Groq chat model if needed.

## Running without an API key (mock mode)

If `ANTHROPIC_API_KEY` is unset, `src/llm_client.py` falls back to
deterministic keyword-based mock responses for classification, drafting,
and judging. This keeps the *repo* runnable and the *harness* exercised
end-to-end (you'll get real JSON files with real structure), but the
*numbers* are not meaningful quality signals — mock mode is functionally
similar to the "simple baseline" by design. This is called out explicitly
in `reports/REPORT.md`, not hidden.

## Architecture

```
customer message
      │
      ▼
 intent classifier (src/intents.py)      -- fixed 7-way taxonomy, LLM call,
      │                                     returns (intent, confidence)
      ▼
 retrieval / grounding (src/retrieval.py) -- TF-IDF top-k over historically
      │                                     resolved threads for this brand
      ▼
 reply drafting (src/drafting.py)         -- LLM call, constrained to what
      │                                     the grounding examples support
      ▼
 escalation policy (src/escalation.py)    -- DETERMINISTIC rules, not an
      │                                     LLM call (see decision log #4/#5)
      ▼
 {intent, confidence, draft_reply, should_escalate, reason, grounding_used}
```

## The 7 intents

`delivery_delay`, `order_status_inquiry`, `refund_or_return`,
`damaged_or_wrong_item`, `account_or_login_issue`,
`billing_or_charge_dispute`, `general_feedback`

Auto-handle-eligible intents: `delivery_delay`, `order_status_inquiry`,
`general_feedback` (everything else always routes to a human — see
`src/config.py` and decision log #4 for why).
