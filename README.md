# AI Support Agent — AmazonHelp (Hiver SDE Intern Take-Home)

An AI support agent for **@AmazonHelp** (from the Kaggle *Customer Support
on Twitter* dataset) that, for each incoming customer message:

1. **Classifies** it into one of 7 defined intents.
2. **Drafts a reply** grounded in how AmazonHelp has historically resolved
   similar issues (retrieved from past resolved threads, not invented).
3. **Decides auto-handle vs. escalate**, with a stated, auditable reason.

Read `reports/REPORT.md` for the full write-up (problem framing, results
vs. baselines, failure analysis, and — importantly — *why the headline
numbers below are not the whole story*). Read `reports/decision_log.md`
for the non-obvious calls made along the way.

## Why there's a bundled sample dataset instead of the real 3M-row file

`data/raw/sample_twcs.csv` is a **220-thread, schema-identical,
structurally-faithful synthetic sample** for AmazonHelp (same `tweet_id /
author_id / inbound / created_at / text / response_tweet_id /
in_response_to_tweet_id` columns, same noisy-tweet style), built because
the real Kaggle file wasn't reachable in the environment this was first
built in. It exists so the whole pipeline — golden set + eval harness —
is runnable end-to-end offline with zero external downloads.

`scripts/download_real_dataset.py` documents how to swap in the real
Kaggle file. The pipeline code (`src/`, `eval/`) is 100% agnostic to
which CSV it's reading, so that's a one-flag change, not a rewrite. See
`reports/REPORT.md` → "What's misleading about my headline number" for
what does and doesn't transfer from the bundled sample to real data.

## Known issues in the current run (fix or disclose before submitting)

These were found by inspecting the actual committed `outputs/` files —
they're real, not hypothetical:

1. **Golden set / calibration set are out of sync.** The checked-in
   `data/golden/golden_eval.csv` was regenerated at a smaller size
   (35 examples) after `data/golden/human_calibration_labels.csv` was
   hand-labelled against an earlier, larger (196-example) golden set.
   Result: `outputs/judge_human_agreement.json` shows only **7 of 30**
   calibration rows actually matched a tweet_id in the current golden
   set — the other 23 were silently dropped by
   `eval/human_agreement.py`'s `if tid not in human` check. **Fix:**
   either regenerate `data/golden/human_calibration_labels.csv` against
   the current golden set (re-run `eval/make_calibration_drafts.py` and
   re-label), or restore the golden set to the size it was when the
   calibration labels were written. Don't submit a judge-agreement number
   based on n=7 without flagging this in the report.

2. **The LLM judge is failing to parse most real Gemini responses.**
   `outputs/eval_results.json` shows judge means around **0.4 out of 5**
   across every rubric dimension — that's not a real quality signal, it's
   the `eval/judge.py` `PARSE_ERROR` fallback (which returns 0) firing on
   most calls. `src/json_utils.py` already strips Markdown fences, so the
   remaining failures are likely a different format issue (e.g. Gemini
   returning prose before/after the JSON in a way `parse_json_object`
   doesn't catch, or truncated output from `max_tokens=250` being too
   low for the rubric's 5-field response). **Fix:** print the raw judge
   response on parse failure to see the actual format, then extend
   `parse_json_object` or increase `max_tokens` in `eval/judge.py`
   accordingly. Until fixed, don't report the judge quality numbers as
   real — they currently measure "how often the judge call cleanly
   parses," not reply quality.

3. **`requirements.txt` lists the deprecated `google-generativeai`
   package** instead of `google-genai`, which is what the code actually
   imports (see Setup section above). A reviewer doing a clean
   `pip install -r requirements.txt` will hit an import error at the
   Gemini step. Fix before submitting — this is exactly the kind of
   "does the README actually reproduce it" gap the assignment is testing.

## Multi-provider LLM support

`LLM_PROVIDER` in `.env` picks the backend; `src/llm_client.py` is the
only file that knows which API is being called — everything downstream
(`src/intents.py`, `src/drafting.py`, `eval/judge.py`) is provider-agnostic.

| Provider | Env vars | Notes |
|---|---|---|
| `anthropic` (default) | `ANTHROPIC_API_KEY`, `HIVER_MODEL` | pay-as-you-go, no strict free-tier rate limit |
| `gemini` | `GEMINI_API_KEY`, `GEMINI_MODEL` | free tier, but as low as 5 req/min — expect auto-retry pauses on a full run (see `src/llm_client.py`'s backoff logic) |
| `xai` | `XAI_API_KEY`, `XAI_MODEL` | OpenAI-compatible endpoint, billed per token |
| `groq` | `GROQ_API_KEY`, `GROQ_MODEL` | OpenAI-compatible endpoint |

Gemini model names get retired without much notice — if the default in
`src/config.py` 404s, check https://aistudio.google.com/ for the current
list and override with `GEMINI_MODEL`.

## Running without an API key (mock mode)

If no matching API key is set, `src/llm_client.py` falls back to
deterministic keyword-based mock responses for classification, drafting,
and judging. This keeps the harness exercisable end-to-end, but the
numbers are not meaningful quality signals — mock mode is functionally
similar to the "simple baseline" by design.

## Architecture

```
customer message
      │
      ▼
 intent classifier (src/intents.py)      -- fixed 7-way taxonomy, LLM call,
      │                                     returns (intent, confidence)
      ▼
 retrieval / grounding (src/retrieval.py) -- TF-IDF top-k over historically
      │                                     resolved threads for this brand
      ▼
 reply drafting (src/drafting.py)         -- LLM call, constrained to what
      │                                     the grounding examples support
      ▼
 escalation policy (src/escalation.py)    -- DETERMINISTIC rules, not an
      │                                     LLM call (see decision log #4/#5)
      ▼
 {intent, confidence, draft_reply, should_escalate, reason, grounding_used}
```

## The 7 intents

`delivery_delay`, `order_status_inquiry`, `refund_or_return`,
`damaged_or_wrong_item`, `account_or_login_issue`,
`billing_or_charge_dispute`, `general_feedback`

Auto-handle-eligible intents: `delivery_delay`, `order_status_inquiry`,
`general_feedback` (everything else always routes to a human — see
`src/config.py` and decision log #4 for why).

## Latest real results snapshot (n=35 golden set, Gemini)

See `outputs/eval_summary.md` for the full table; headlines, with honest
caveats:

- Agent intent accuracy: **0.457** — currently *below* the hand-written
  keyword baseline's **0.743**. `general_feedback` scored 0.0
  precision/recall (every example misclassified) — a real, specific
  failure mode worth writing up in `reports/REPORT.md`, not smoothing over.
- Escalation precision is low (0.167) for the same structural reason
  documented in `reports/REPORT.md` §3 failure #1 (policy-excluded
  intents always escalate, regardless of whether the golden label agrees).
- Judge quality scores are not currently trustworthy — see "Known issues"
  item 2 above.

This snapshot is small (n=35) and mid-debugging — treat it as a
work-in-progress signal, not the number to put in the report's headline
results table. Fix the known issues, re-run, and update
`reports/REPORT.md` §2 and §3 with the corrected numbers before
submitting.
