# Report — AI Support Agent for AmazonHelp

Numbers below are from `outputs/eval_results.json` and
`outputs/judge_human_agreement.json`, generated by `python3 run_pipeline.py`
in **mock mode** (no `ANTHROPIC_API_KEY` set in this environment — see
"What's misleading about my headline number", section 4, before trusting
any number in this report at face value).

## 1. Problem framing

**Brand chosen:** AmazonHelp. High volume, high variety of issue types
(shipping, refunds, account, billing), and a visible house style in its
replies ("DM us your order number") — good for testing whether grounding
actually constrains generation instead of the model freelancing.

**What "good" means for this brand, concretely:**
- A **wrong intent** is cheap if the drafted reply is still reasonable
  (e.g. confusing `refund_or_return` with `damaged_or_wrong_item` — both
  route to "DM your order number"). A wrong intent is expensive when it
  causes the wrong *escalation* decision.
- A **hallucinated promise** (a refund amount, a delivery date, a policy
  that doesn't exist) is the single worst failure mode for a brand account
  — it's public, and it creates a commitment support has to honor or
  publicly retract.
- **Under-escalating** an angry/legal/fraud-adjacent message is worse than
  over-escalating a mundane one. The cost function is asymmetric, and the
  escalation policy (section 3, `src/escalation.py`) is written to be
  asymmetric on purpose: several hard keyword triggers force escalation
  regardless of the classifier's confidence.

**What I chose not to build:**
- No fine-tuning — a prompted classifier + retrieval-grounded drafting is
  the right complexity level for a brand-specific agent built in a
  take-home timeframe, and it's easier to audit/change (decision log #6, #9).
- No multi-turn conversation state / memory across a whole thread beyond
  the single most recent customer message + retrieved grounding — real
  production Hiver-style agents would need this, but it roughly doubles
  the scope (thread summarization, turn-taking policy) for a take-home.
- No actual auto-send to Twitter — the deliverable is "draft + decision",
  not "act unsupervised on a brand's public account." Even `auto_handle`
  messages produce a draft a human could spot-check in a real deployment.
- No support for brands other than AmazonHelp in this pass, though nothing
  in `src/` is AmazonHelp-specific except the config constants.

## 3. Failure analysis — top 5 failure modes

1. **Escalation precision collapses because the policy conflates "policy-
   excluded intent" with "true need to escalate."** The agent escalates
   100% of `account_or_login_issue`, `billing_or_charge_dispute`, and
   `refund_or_return` messages by design (a bot shouldn't have refund/account
   authority), but only 23/196 golden examples were *labelled* as
   needing escalation (those with an explicit anger/legal/manager trigger
   phrase). Result: 100 false positives, precision 0.19. **This is a
   genuine design tension, not a bug** — but it means "escalation
   precision" as measured here conflates two different questions ("is this
   message urgent?" vs. "is this the kind of issue a bot should ever
   resolve unsupervised?"). Fix: report these as two separate metrics.

2. **`order_status_inquiry` has the worst precision (0.51) of any intent**
   — it's the default fallback in both the mock classifier and the simple
   baseline, so anything ambiguous gets dumped there. In a real LLM run
   this specific failure mode should mostly disappear (the fallback is a
   mock-mode artifact), but it flags that `order_status_inquiry` is the
   taxonomy's "catch-all" and needs a tighter definition or an explicit
   `other/unclear` intent (see section 5).

3. **`account_or_login_issue` and `billing_or_charge_dispute` have strong
   precision but weak recall (0.43, 0.36)** — messages in these categories
   often *also* mention an order number or a delivery timeframe, and the
   keyword-driven mock classifier grabs the more common trigger words
   first. A model with actual reasoning (vs. mock keyword matching) should
   do meaningfully better here, but it's a reminder that intent boundaries
   overlap in real customer language and a single-label taxonomy will
   always lose some signal.

4. **Reply drafting can be badly tone-mismatched on `general_feedback`.**
   In mock mode, every draft is the same generic "sorry for the trouble,
   DM your order number" template — including for messages like *"your
   support team was amazing today, thank you"*. That's an extreme (mock-
   mode-only) version of a real risk: a drafting step that isn't
   conditioned tightly enough on intent will default to its most common
   pattern (apologize + ask for info) even when the right response is
   "thank you, we'll pass this along." This is exactly why the judge
   rubric has a dedicated `tone` dimension.

5. **The judge is degenerate in mock mode (outputs a constant 3.0 for
   every reply, every dimension), so it cannot distinguish a good reply
   from a bad one.** Discovered directly via the human-agreement
   calibration (section 4) — judge/human exact-match was only 20%, and
   Pearson correlation is undefined (the judge has zero variance to
   correlate with). This is not a subtle bug; it's the expected
   consequence of running the "judge" through the same mock fallback as
   everything else, and it's the clearest evidence in this whole report
   that a real API key is a prerequisite for any of these numbers meaning
   anything.

## 4. What is misleading about my headline number

This section is mandatory in the brief and deserves to be read literally,
because in this specific submission almost every number above is a
placeholder, and here's exactly how:

- **Every number in section 2 was generated with no `ANTHROPIC_API_KEY` set**
  (this sandbox has no network path to Anthropic's API). Both the intent
  classifier and the reply drafter fell back to `src/llm_client.py`'s
  mock mode — deterministic keyword heuristics, not an LLM. **The 0.781
  "agent" intent accuracy is barely above the 0.776 hand-written keyword
  baseline for a structural reason: the mock classifier IS a hand-written
  keyword matcher, nearly identical to the simple baseline's.** This
  comparison currently proves almost nothing about whether an LLM adds
  value over rules — it only proves the harness plumbing works end-to-end.
  The real test is `python3 run_pipeline.py` with a live key.
- **The escalation "simple baseline" scores a perfect 1.00 across the
  board, which looks suspicious because it is.** The golden set's
  escalation ground truth was generated (see `eval/build_golden_set.py`)
  using the *same* hard-keyword-trigger rule that both the simple baseline
  and part of the agent's policy use. So the simple baseline isn't
  "surprisingly good at escalation" — it's answering a question that was
  defined in its own image. A real test of escalation quality needs
  human-judged escalation labels (does a person think this needs a
  human?) that are independent of any keyword list, which the current
  golden set does not have.
- **The golden set itself is built from a synthetic, template-generated
  sample dataset** (see README, "Why there's a bundled sample dataset"),
  not the real 3M-row Kaggle corpus. Real Twitter support threads are
  messier: multi-turn, off-topic tangents, sarcasm, multiple issues in one
  tweet, agents handing off between each other. All of the numbers above
  are close to an upper bound on how clean the classification problem is;
  expect real-data accuracy to be meaningfully lower.
- **The reply-quality judge scores (flat 3.0s) are not a quality signal
  at all** in this run — see failure mode #5. A judge with zero output
  variance cannot be "3.0 out of 5 good" or bad; it's just broken in this
  configuration. Don't read anything into it beyond "the harness ran."
- **n=196 golden / n=40 judge subsample / n=30 calibration set** are all
  fine sample sizes for a take-home but too small to support strong claims
  about production-grade precision, especially per-intent (28 examples per
  intent means a couple of misclassifications move F1 by several points).

## 5. What I'd do next with one more week

1. **Re-run everything with a real API key** and treat this report's
   numbers as void until that happens — that's the single highest-value
   next step, not a nice-to-have.
2. **Decouple "urgency/should-escalate" labels from the keyword list used
   to build them.** Get an independent human rater to label 100-150 real
   examples for "would you want a human to see this before it's handled?"
   without seeing the keyword-trigger list, and re-measure escalation
   precision/recall against that.
3. **Add an explicit `other/unclear` intent** so the classifier has a
   legitimate low-confidence exit instead of defaulting into
   `order_status_inquiry`, and route `other/unclear` straight to
   escalation.
4. **Swap TF-IDF retrieval for embeddings** (interface in
   `src/retrieval.py` is already isolated for this) and measure whether
   grounding quality (the judge's `grounded` dimension) actually improves
   — TF-IDF misses paraphrases (e.g. "hasn't shown up" vs. "never
   arrived") that an embedding model would catch.
5. **Get the real Kaggle dataset in and re-derive the golden set from real
   threads**, hand-labelled by an actual human going through them (the
   sampling methodology in `eval/build_golden_set.py` transfers directly;
   only the labelling step needs to become manual).
6. **Widen the judge rubric's calibration set past 30 examples and get a
   second human rater** to compute inter-rater reliability before trusting
   judge-vs-human agreement numbers.
7. **Add a lightweight "did the draft contradict the grounding" automatic
   check** (e.g. flag any dollar amount / date in the draft that doesn't
   appear in the grounding examples) as a cheap, deterministic backstop
   the judge's `grounded` dimension is trying to catch semantically.
